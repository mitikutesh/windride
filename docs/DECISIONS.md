| DEC-033 | **Device-compass heading (blend with GPS travel bearing)** (task #32, post-backlog enhancement; reviewed by a substitute senior reviewer on Opus — Fable 5 out of usage credits). Google-Maps-style "which way the phone points": `nav/compass.ts` `CompassHeadingSource` wraps DeviceOrientation (injectable target + permission requester, like `locationService.ts` wraps geolocation) and `nav/heading.ts` `blendHeading(travelDeg, compassDeg, speedMs)` crossfades the two into `RideState.headingDeg`. Decisions: (a) **Speed is the arbiter, not a fixed source.** At cycling pace the GPS track bearing is truth (the magnetometer points wherever the phone sits in a bag/pocket); when stopped the GPS course is noise and the compass is all there is. `blendHeading` crossfades linearly by speed — full compass below `HEADING_GPS_TRUST_LOW_MS` (0.8 m/s ≈ 2.9 km/h), full GPS travel at/above `HEADING_GPS_TRUST_HIGH_MS` (3.0 m/s ≈ 10.8 km/h) — on the unit circle so it wraps across 0°/360°. Null compass → travel; null travel → compass; both null → null. This keeps the existing GPS-only behaviour identical whenever the compass is unavailable. (b) **Compass reading.** iOS Safari's `webkitCompassHeading` is already true-north clockwise and used directly; other browsers' absolute `deviceorientationabsolute.alpha` (CCW from north) is converted `(360 − alpha)`; relative-only orientation (no absolute heading) is dropped, not guessed. Readings are circular-EMA smoothed (`HEADING_EMA_ALPHA`) to tame magnetometer jitter. **Known limitation:** the alpha→heading conversion assumes a roughly-flat phone in default screen orientation — full tilt/screen-orientation compensation (what Maps does) is a deferred refinement; the GPS bearing carries the load whenever the rider is actually moving, so the approximation only shows while stopped. (c) **iOS permission** (`DeviceOrientationEvent.requestPermission`) is requested inside the Start/Resume user gesture (required by iOS); denial or unsupported is silent — the GPS travel bearing still drives the arrow, no nag. (d) **Between-fix updates:** `RideController.setCompassHeading(deg)` returns the freshly-blended heading so the map arrow rotates when a stopped rider turns the phone, without waiting for the next GPS fix (which may never come while stationary). The wind HUD and off-route arrow read the same blended `headingDeg`, refreshed per fix. (e) **Boundary:** the sensor lives in `nav/**` (which may touch DOM, as geolocation already does), not `adapters/**` (that rule is fetch-specific); the blend math is pure and unit-tested; no live sensor is touched in tests (target + requester injected). **Review addendum** (substitute Opus review, standing in for Fable 5 — out of credits; verdict ship-able, no MAJORs): `circularBlend` now returns the dominant-weight endpoint when the two angles are ~opposite (`BLEND_DEGENERATE_MAG`) instead of an `atan2` that whips ~180° on noise — the "phone points backwards while accelerating from a stop through the crossfade band" case, and equally any U-turn passing through the GPS-bearing EMA; and `compassHeadingOf` honours a reading's alpha when it arrived on the `deviceorientationabsolute` event even if the browser omits the `absolute` field (some do), so the compass isn't silently dead there.
